# 03 — Каталог блюд

Каталог — основной контент приложения, и ведётся он вручную через коммиты. Этот файл описывает соглашения, которые делают такое ведение устойчивым, а в конце — второй слой, свои блюда, который заводится с телефона и живёт по другим правилам.

## Рабочий процесс

1. Приготовил или взял готовую еду.
2. Сфотографировал порцию — так, как реально её ешь. Тарелка целиком, сверху, при дневном свете.
3. Скинул фото в `raw-photos/` под именем будущего `id`: `rice-beef.jpg`.
4. Прикинул калорийность **этой порции** и записал.
5. `pnpm foods:optimize` — сжимает фото в `public/foods/rice-beef.webp`.
6. Добавил объект в массив `foods` в `src/entities/food/lib/catalog.ts`.
7. `git commit && git push` — GitLab CI собирает и деплоит, телефон подхватывает при следующем открытии.

Ограничение принято сознательно: чтобы завести блюдо, нужно быть за компьютером. Взамен каталог остаётся вычищенным, а не превращается в свалку из «еда 1», «еда 2».

## Соглашения по `id`

Слаг в kebab-case, латиницей, по схеме `основа-дополнение`:

```
coffee-black      кофе чёрный
coffee-milk       кофе с молоком
egg-boiled        яйцо варёное
egg-fried         яичница
rice-beef         рис с говядиной
rice-chicken      рис с курицей
buckwheat-chicken гречка с курицей
```

**`id` неизменяем и не переиспользуется.** Он записан в исторические записи дневника пользователя, которые лежат на телефоне и правке не подлежат. Переименование `id` = потеря связи с фотографией у всех прошлых записей.

Название (`name`) менять можно свободно — в записях лежит его снапшот.

## Порция как единица учёта

Одна карточка = одна типичная порция. Не «100 г риса», а «моя тарелка риса с говядиной».

Отсюда следует, что каталог получается **на уровне готовых блюд, а не ингредиентов**: «рис с говядиной» и «рис с курицей» — две отдельные карточки со своими фото и своей калорийностью. Это осознанный размен: больше карточек, но ноль арифметики в момент приёма пищи.

За год каталог реалистично вырастает до 150–300 позиций. Экран добавления обязан оставаться удобным при таком объёме — см. [05-screens.md](05-screens.md).

Множественность выражается количеством: два яйца — это `egg-boiled` × 2, а не отдельная карточка «два яйца».

**Фото необязательно.** У большинства блюд оно есть и служит основным способом выбора, но бывает еда без постоянного облика — «конфета» сегодня карамель, завтра трюфель. Снимать одну конкретную ради карточки бессмысленно: фотография обещала бы точность, которой в самой записи нет. У такого блюда `photo` не заполняется, и миниатюра показывает первую букву названия. Это состояние отличается от «фото ещё не сделал» тем, что оно окончательное, поэтому и выражено отсутствием поля, а не ссылкой на несуществующий файл.

## Категории

```ts
// src/entities/food/lib/categories.ts
export const categories = [
	{ id: "meals", name: "Основное" }, // рис с мясом, супы, паста
	{ id: "basics", name: "Простое" }, // яйца, творог, бутерброд
	{ id: "drinks", name: "Напитки" }, // кофе, чай, сок
	{ id: "snacks", name: "Перекусы" }, // шоколад, орехи, фрукты
	{ id: "outside", name: "Не дома" }, // покупное и общепит
] as const;

export type CategoryId = (typeof categories)[number]["id"];
```

Список намеренно короткий и плоский. Категории — это фильтр-чипсы в одну строку, а не дерево.

## Фотографии

**Требования к результату:** ширина 600 px, WebP, качество 80, ~40–60 КБ на файл. Квадратный кроп по центру — сетка выбора состоит из квадратов.

Почему это важно: все фото попадают в прекэш service worker'а, чтобы приложение работало офлайн. 300 блюд × 50 КБ ≈ 15 МБ — приемлемо. Те же 300 фото прямо с камеры без сжатия — это 1,5 ГБ, приложение просто не установится.

**Скрипт `scripts/optimize-foods.mjs`** (реализуется на этапе 1):

```js
// pnpm foods:optimize
// raw-photos/*.{jpg,jpeg,png,heic} -> public/foods/<basename>.webp
import { readdir, mkdir } from "node:fs/promises";
import { join, parse } from "node:path";
import sharp from "sharp";

const SRC = "raw-photos";
const OUT = "public/foods";
const SIZE = 600;

await mkdir(OUT, { recursive: true });
const files = (await readdir(SRC)).filter((f) =>
	/\.(jpe?g|png|heic|webp)$/i.test(f),
);

for (const file of files) {
	const { name } = parse(file);
	await sharp(join(SRC, file))
		.rotate() // учесть EXIF-ориентацию
		.resize(SIZE, SIZE, { fit: "cover", position: "centre" })
		.webp({ quality: 80 })
		.toFile(join(OUT, `${name}.webp`));
	console.log(`✓ ${name}.webp`);
}
```

`raw-photos/` добавляется в `.gitignore`: исходники с телефона в репозиторий не попадают, коммитятся только сжатые webp.

`.rotate()` без аргументов обязателен — иначе фотографии с телефона, снятые вертикально, окажутся лежащими на боку: браузеры уважают EXIF-ориентацию, а sharp при ресайзе её отбрасывает.

## Проверка целостности

Каталог редактируется руками, поэтому нужна защита от типовых ошибок. Тест `src/entities/food/lib/catalog.spec.ts`, падающий на:

1. дубликатах `id`;
2. `id`, не соответствующем `^[a-z0-9]+(-[a-z0-9]+)*$`;
3. отсутствующем файле `public/foods/<photo>`;
4. осиротевшем файле в `public/foods/`, на который не ссылается ни одно блюдо;
5. `kcal <= 0` или нецелом;
6. неизвестном `category`.

Запускается вместе с остальными тестами (`pnpm test:unit`), в CI — перед сборкой. Стоит полчаса работы и снимает целый класс ошибок «задеплоил, а на телефоне битая картинка».

## Архивация

Перестал готовить блюдо — `archived: true`, а не удаление. Карточка исчезает из выбора, но остаётся доступной для отображения старых записей: фото и категория подтягиваются, история выглядит целой.

Удалять запись из `foods.ts` допустимо только если блюдо было заведено по ошибке и заведомо ни разу не попало в дневник ни на одном устройстве.

## Свои блюда

Каталог требует быть за компьютером. Это верно для еды, которая повторяется, и неверно для всего остального: пирог у бабушки, кафе в незнакомом районе, пачка печенья из магазина у дома. Ждать вечера, чтобы записать съеденное днём, значит не записать его вовсе.

Поэтому рядом с каталогом живёт второй слой — `customFoods` в IndexedDB (см. [02-data-model.md](02-data-model.md)). Заводится он прямо во время еды, на экране «Своё блюдо»: название, калорийность, необязательное фото с камеры или из галереи.

**Чего у своего блюда нет и почему.**

- **Категории.** Чипсы придуманы, чтобы разложить полторы сотни карточек. Своих блюд единицы, и у них есть собственный чипс «Своё» — раскладывать внутри нечего.
- **Тегов.** Поиск по ним имеет смысл, когда название не угадывается («мясо» → «рис с говядиной»). Своё блюдо пользователь назвал сам десять секунд назад и помнит слово, которым назвал.
- **Архивации.** Она нужна каталогу, потому что удаление из репозитория — операция для всех устройств и на все времена. Здесь удаление — обычная кнопка, и записи после него остаются целыми.
- **Слага.** `id` — `crypto.randomUUID()`. Слаг существует, чтобы человек читал каталог глазами в diff’е; в базе на телефоне читать некому.

**Фото хранится целиком в блюде**, строкой data URL, сжатое до 400 px. Файла в `public/foods/` для него нет и быть не может: сборка про это блюдо не знает. Отсюда и разница в размере с каталожными 600 px — снимок из базы показывается только миниатюрой, а весит он ровно столько, сколько занимает в выгрузке.

**Правка не переписывает историю.** Поменял калорийность — новые записи пойдут с новой, старые останутся с прежней: в них лежит снапшот (инвариант 1 из [02-data-model.md](02-data-model.md)). То же с названием. Единственное, что правка меняет задним числом, — миниатюра, потому что фото читается из блюда, а не из записи.

**Каталог и свои блюда не смешиваются.** Своё блюдо нельзя «повысить» до каталожного кнопкой — если еда прижилась и повторяется, она заводится в `catalog.ts` обычным порядком, с нормальным фото и слагом. Автоматический перенос выглядел бы удобным ровно до первого раза, когда в репозиторий уехало бы блюдо с именем «еда» и снимком из-под стола.
